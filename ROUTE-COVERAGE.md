## Local backend target

`.env.local` (ignored by `.gitignore`) points at the lab:

```
NEXT_PUBLIC_API_URL=https://evaka.test:4444/v1
```

`src/lib/api/base-url.ts` is now the only place the base URL is resolved. There
is **no default backend**: if `NEXT_PUBLIC_API_URL` is unset the proxy, the API
client and the media resolver fail explicitly instead of calling the retired
Vercel deployment.

Lab TLS is a private CA, so trust must be installed rather than bypassed.
Operator actions (need `sudo`, not performed by this repository):

```bash
# 1. Hostname (one line, lab VM only)
echo '192.168.220.129 evaka.test' | sudo tee -a /etc/hosts

# 2. Trust the lab CA (repo copy: deploy/tls/lab-ca.pem in the backend repo)
sudo cp deploy/tls/lab-ca.pem /usr/local/share/ca-certificates/viora-lab-ca.crt
sudo update-ca-certificates

# 3. Firefox uses its own store: Settings → Privacy & Security → Certificates
#    → View Certificates → Authorities → Import → viora-lab-ca.pem
```

Node scripts accept the CA without system changes:

```bash
VIORA_CA_CERT=<backend>/deploy/tls/lab-ca.pem \
VIORA_RESOLVE=evaka.test:192.168.220.129 \
NEXT_PUBLIC_API_URL=https://evaka.test:4444/v1 \
node scripts/api-smoke/run.mjs
```

### Contract audit

`scripts/api-smoke/contract-audit.mjs` extracts every static `apiClient`
path/method from `src/` and checks it against `<origin>/docs-json`.

Latest run: `CONTRACT_CALLS=314 CONTRACT_PATHS=487 UNKNOWN=5 METHOD_MISMATCH=2`.

All seven findings are **deployed-backend drift, not frontend errors**:

- `GET/POST /admin/auth-providers*` (5 paths) exist in backend source
  (`src/modules/auth/auth-provider-admin.controller.ts`, registered in
  `auth.module.ts`) but are absent from the running deployment's OpenAPI.
- `POST /store/equip/{inventoryId}` and `POST /store/admin/items/{id}/assets`
  exist in backend source; the deployed spec lists only the sibling
  `DELETE /store/equip/{slot}` and `PATCH /store/admin/items/{itemId}/assets`,
  and the audit compares paths with parameter names normalised.

Redeploying the backend is what closes this gap; nothing in the dashboard
should be "fixed" to match an older deployment.

## Security flows

### MFA (`/security`)

`GET /auth/mfa/factors`, `POST /auth/mfa/enroll`, `POST /auth/mfa/challenge`,
`POST /auth/mfa/verify`, `POST /auth/mfa/verify-enable`, `POST /auth/mfa/disable`.

Enrollment shows the returned QR/secret in memory only — never persisted to
storage, logged, or placed in a URL. MFA is enabled only after `verify-enable`.
An enrolled factor is not treated as proof that the current session satisfies
the policy. Global/role MFA policy APIs are absent from the backend, so no
administrative policy switches are rendered.

### Account deletion

`POST/GET/DELETE /auth/account/deletion`. Self-service only; administrative
moderation of another user stays in `/dashboard/users`. Cancellation is offered
only while the request is still cancellable, per the backend's status field.

### Devices

`GET/POST /auth/devices`, `DELETE /auth/devices/{deviceId}`,
`POST /auth/devices/fcm-token` (service method only). No FCM token UI is
exposed: a real Firebase registration token is required and none exists in this
environment, so inventing one would be a fake registration.

### OAuth providers (`/security`)

`GET /admin/auth-providers`, `GET /admin/auth-providers/:provider/revisions`,
`POST …/:provider/validate|stage|rollback`, `POST …/revisions/:id/retry`.

- Status and revision history are read-only and secret-free (`secretSet` +
  client-id hash, never the secret).
- Stage/validate accept a JSON config and three write-only secret inputs; empty
  inputs mean "keep the stored secret".
- A `STAGED` revision is rendered as staged, never as active: activation is
  performed by the host-side auth-provider agent recreating the Auth service.
- Rollback requires an `APPLIED` revision and asks for confirmation; retry is
  offered only for `FAILED`/`ROLLED_BACK`.

Blocked prerequisites: `AUTH_PROVIDER_SECRET_KEY` (32 bytes, hex or base64,
AES-256-GCM) is absent from the backend environment, and no real Google/
Facebook/Apple credentials exist. Both are backend/operator values; the
dashboard does not fabricate them.

The running deployment also predates the control plane: its `/docs-json` has no
`/admin/auth-providers` operations, so the panel reports a 404 there until the
backend is rebuilt from source (the controller is registered in
`src/modules/auth/auth.module.ts`).

### OAuth user login — backend gap

`GET /auth/google/url` and `GET /auth/facebook/url` return the provider URL and
the dashboard initiates the flow. The return leg cannot complete on the current
backend: `PUBLIC_BASE_URL`/`GOOGLE_REDIRECT_URL`/`FACEBOOK_REDIRECT_URL` point at
`https://192.168.220.129/v1/auth/{provider}/callback`, while only **POST**
callback handlers are exposed. A provider redirect is a GET, so it is rejected
before the code exchange. This is a backend contract gap plus missing provider
credentials, not a dashboard workaround target.
