## 2. Agents & Distribution — `modules/agents/*`

**Distribution is a real, separate entity — not just an Agent operation.** Evidence:
- `MasterDistributorProfile` (`master_distributors`): own `userId`, `status: pending|active|suspended|closed`, `capabilities[]`, `allowedRegions[]`.
- `DistributorAgentAssignment` (`distributor_agent_assignments`): `distributorId ↔ agentId`, one active distributor per agent — genuine two-tier hierarchy (Distributor → Agent → Player).
- `FinancialAccount.ownerType` enum: `'user'|'agent'|'platform'|'distributor'|'escrow'` — ledger treats distributor as its own account owner class.
- 4-tier rate model: `providerPurchaseRate, distributorSellRate, agentCustomerSellRate, customerCashoutRate`.

**Commissions — found**, `AgentCommissionPolicy` (`agent_commission_policies`): `version(unique), status: draft|pending_approval|active|retired, commissionBps(0-10000), fundingAccountOwnerId`. Used in `agents.service.ts` settlement logic. **Not** present anywhere in `wallet` or `gifts` modules (gifts has a differently-named "revenue split" mechanism, not "commission").

## 3. Wallet / Financial — `modules/wallet`, `modules/reconciliation`, `modules/iap`

**Money representation**: every monetary field is a `numeric(30,0)` column surfaced as a **string** (`FinancialAccount.balance`, `LedgerEntry.amount/balanceBefore/balanceAfter`, `Wallet.gameCurrency`) or `bigint` (`WalletTransaction.amount`) — never native float. `AdjustBalanceDto.amount` validated `^[1-9][0-9]*$`.

`wallet.controller.ts` (`@Controller('wallet')`, auth only, no admin permission): `GET /wallet`, `GET /wallet/transactions` — user-facing only.

`currency-display.controller.ts` (`admin/currency-display`): `GET` (`admin.read`), `PUT` (`configs.write`) — display metadata only, "never balances or ledger history" per code comment.

`currency-display-public.controller.ts`: `GET /currency/display`, public.

`reconciliation.controller.ts` (`admin/financial-reconciliation`): `GET findings` (`reports.read`, `limit`), `POST run` (`reports.execute`+`financial.execute`). `FinancialReconciliationFinding.status: open→acknowledged/resolved/false_positive`, `severity: info|warning|critical`.

`iap.controller.ts`: `POST /iap/verify` (auth only), `POST /internal/iap/revocation` (webhook secret, no user auth). **No admin controller for IAP at all** — no admin read/list of IAP purchases.

**Admin wallet-adjust endpoint is `POST /admin/users/:id/balance`** (see §1) — not a separate `/wallet/admin/*` route.

**VERDICT: Full**, with a genuine double-entry ledger (`FinancialAccount`+`LedgerEntry`) that coexists with an older, simpler `Wallet`/`WalletTransaction` projection. IAP has no admin surface (gap for section 23 "financial admin home" if IAP data is expected there).

## 6. Achievements & Tasks — **NOT FIRST-CLASS BACKEND ENTITIES**

> **Correction (2026-08-16, direct source re-verification during Phase 2C implementation):**
> A repo-wide search for `@Controller('achievements'` across the entire backend `src/`
> returns **zero matches**. There is no achievements controller anywhere — not just no
> admin CRUD. This means `GET /achievements`, `/achievements/me`, `/achievements/me/unlocked`,
> `/achievements/me/incomplete`, `/achievements/me/rare`, and `POST /achievements/:id/claim`
> (all referenced by the frontend's `achievements.service.ts`, previously assumed to be
> working public/self-service reads) **do not exist either**. The entire achievements
> domain — admin AND self-service — has no backend route surface. The only real backend
> touchpoint for achievement data is `RuleDefinition.kind='ACHIEVEMENT'` via
> `RuleAdminController` (admin authoring only, no list/detail) and the generic
> `GET /progress?kind=ACHIEVEMENT` self-service progress query.

`src/modules/achievements/{dto,entities}/` are **completely empty** — zero files. No achievements controller/service/entity exists anywhere. Grep for `"achievement"` in `*.controller.ts` hits only the `gameplay-events` rule-engine controllers (§5). **Achievements = `RuleDefinition.kind='ACHIEVEMENT'`**, unlocked via the `UnlockAchievement`/`UpdateAchievementProgress` action nodes. **There is no `/admin/achievements` route anywhere in the backend.**

A supplementary pair, `TaskStageDefinition`/`TaskStageProgress(Receipt)` (`gameplay-events/entities/task-stage.entity.ts`), supports multi-stage tasks as sub-records of a `RuleDefinition` — no dedicated stage-authoring endpoint found; presumably authored inside `graphDefinition`.

**VERDICT: Achievements domain does not exist as a backend module — `modules/achievements` is empty scaffolding. Tasks likewise have no standalone entity/controller.** Any admin UI for either must be built against `RuleAdminController` (`kind=ACHIEVEMENT` / `kind=TASK`) plus the Reward Bundle V2 / Node Registry editors, not a bespoke achievements/tasks CRUD API.

**System Health** — `src/modules/common/controllers/health.controller.ts` (note: lives under `modules/common`, not `src/common` as commonly assumed): `GET health` (public), `GET health/ready` / `health/metrics` / `health/redis` / `health/system` (all `admin.read`), `POST health/reset-circuits` (`admin.write`, resets Supabase/Redis/DB/Firebase circuit breakers).

**Audit** (`modules/audit`) — `audit.service.ts` implements `findByActor`, `findRecent`, `findByTarget`, `findByActionType` (all fully working queries) **but no controller file exists in this module at all**, and grep across every controller in the repo for `AuditLog` returns zero hits. **Audit is captured but has zero HTTP read endpoints.** A frontend Audit page cannot be built without a new backend controller being added first.

**VERDICT**: Configs and System Health **Full**. Notifications has **no admin surface** (self-service only). Audit is **write-only internally / no read API** — this is a genuine backend gap, not a frontend one.

## 11. Users / Auth admin surface

`users.controller.ts` admin-relevant: `GET users/search` (`users.read`, "Admin only"), `GET users/:immutableUserId` (`users.read`). All other routes (`me`, `me/bootstrap`, `me/permissions`, `me/profile`, `me/xp`, `me/level`, `me/rank`, etc.) are self-service. The actual admin user-management surface (list/detail/inventory/purchases/status/role/balance/refund) lives in `admin.controller.ts` (§1) — `users.controller.ts` is thin.

`auth.controller.ts` has no user-management endpoints; its only `RequirePermissions`-gated route is a dev-mode toggle (`configs.write`), unrelated to admin user management.

**No `AdminUser` entity** (confirmed, zero grep hits). Admin-ness = `User` + privileged `user_roles` rows, resolved by `PermissionEngineService`.

**VERDICT: Full**, split across two controllers (`users.controller.ts` for search/lookup, `admin.controller.ts` for the actual CRUD).
